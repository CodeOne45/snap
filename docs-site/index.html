Your agent keeps re-deriving things it already solved

Ask it to scaffold "a service like the other ones," or wire up Sentry for the fifth repo this month, and it regenerates the boilerplate from scratch — burning tokens, occasionally missing a case form of the project name. Snap turns a verified project or change into something applied deterministically instead.

snap new api-service northwind-payments --var name=northwind-payments ✓ 31 files · 42.0 KB · ~11.8k tokens written by Snap instead of the agent
snap add sentry northwind-payments --var service=payments + file src/lib/sentry.ts (35 bytes) ~ file package.json (105 bytes) ~ file .env.example (27 bytes) » hook npm install ✓ 4 files · 329 B · ~132 tokens written by Snap instead of the agent

Two primitives

Both usable from the CLI, the TUI, or an MCP server an agent calls directly.

templates — snap new

Capture a working project once; generate byte-identical new ones from it forever. No blank-slate re-scaffolding, no cp -r and grep-for-the-old-name.

recipes — snap add

Capture one verified change — new files, a dependency, an env entry, a hook — and apply it to any other existing project. One call instead of re-deriving it.

Why an agent (or you) would want this

  • Deterministic, not generative. Same template/recipe version and inputs → byte-identical output, every run — nothing to get subtly wrong on the fifth repetition.
  • Verified once, reused forever. A template declares [test] — a real build/test command run before anyone trusts it. Recipes are getting the same discipline next.
  • A cost you can point at. Every apply prints a token/byte receipt, and snap stats totals what Snap wrote instead of the agent, across CLI and MCP.
  • Capture, not authoring. Point it at a real project or commit; it detects placeholders and dependency edits itself. No templating config to hand-write.

Install

git clone https://github.com/CodeOne45/snap
cd snap
make build
./snap --version

Or via a package manager, once a release is published — see the README.

How it's built

Every command builds an immutable plan — the ledger you saw above — before anything is applied; --dry-run and --json both just print that same plan instead of applying it. The CLI, TUI, and MCP server are thin adapters over the same core use cases, so there's exactly one place any of this logic lives.
