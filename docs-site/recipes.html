Recipes

A template creates a new project. A recipe applies a reusable change to an existing one: new files, dependency additions, env entries, and post-apply hooks. A recipe is a plain directory — a recipe.toml manifest plus an optional files/ directory — living under ~/.config/snap/recipes/, fully hand-editable, or produced by snap capture --from-commit (in progress).

Manifest

[recipe]
name = "sentry"
version = "1.0.0"
description = "Error tracking with Sentry"

# Recipe applies only if every listed file already exists
[applies_to]
files = ["package.json"]

[[variables]]
name = "service"
prompt = "Service name"
default_from = "project.name"     # resolved from the target's own .snap/origin.toml

[[dependencies]]
ecosystem = "npm"                 # npm | go | pip | cargo
name = "@sentry/node"
version = "^8.0.0"
dev = false

[[env]]
file = ".env.example"
key = "SENTRY_DSN"
value = ""

[[hooks.post]]
run = "npm install"

Applying one

snap add sentry                        # apply to the current directory
snap add sentry ~/code/northwind-site --var service=payments
snap add sentry --dry-run
snap add sentry --json
snap recipes                            # list available recipes (alias: snap list --recipes)

Dependency editors

Dependency edits are format-preserving (internal/core/deps), never a shelled-out package manager call: package.json keeps its key order and indentation; go.mod is edited via golang.org/x/mod/modfile; Cargo.toml's [dependencies]/[dev-dependencies]; pip picks whichever of pyproject.toml's [project].dependencies or requirements.txt is present (pyproject.toml preferred when both exist). Installing is a [[hooks.post]] command, gated the same way a template's hooks are.

All-or-nothing, and idempotent

Applying collects every conflict — applies_to not satisfied, a new file already present with different content, a dependency already pinned to a different version, an env key already set to a different value — and fails with the full list rather than writing part of a recipe. Re-applying a recipe whose files, dependencies, and env entries are already exactly present is a no-op: snap add reports it and writes nothing.

Provenance

A successful apply appends a [[recipes]] entry to the target's .snap/origin.toml — created with only this field if the project wasn't generated by Snap at all:

[[recipes]]
name = "sentry"
version = "1.0.0"
source = "local"
applied_at = 2026-11-02T10:00:00Z
[recipes.variables]
  service = "payments"

Verification, in progress

A recipe will be able to declare the same [test] block a template already can — a real build/test command, run after applying, rolled back byte-identically if it fails. Today, applying trusts that the recipe's author already verified it; this closes that gap.

Capturing one from a commit

snap capture --from-commit is in progress: turn a commit that added something (new files, a dependency, an env key) in one project into a recipe that applies cleanly to another, same-stack project. Secrets are excluded by the same rules as capturing a whole project.
